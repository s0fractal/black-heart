## 1. Онтологічний розрив: Чому смарт-контракти зазнали краху, а PDF застряг у минулому столітті

### 1.1. Помилка «Code is Law»
Хвиля блокчейн-ейфорії запропонувала догму: *«Код є законом»*. Всі юридичні зобов'язання спробували втиснути в байткод віртуальних машин (EVM, WASM).

Цей експеримент зазнав поразки з трьох фундаментальних причин:
1. **Викидання людського субстрату:** Байткод не містить наміру (*intent*), передісторії, преамбули, форс-мажорів та суб'єктивного контексту сторін. Він сліпий до юрисдикцій і реального фізичного світу.
2. **Недоступність для правосуддя:** Жоден суддя, арбітр або навіть сторона угоди без спеціальної інженерної підготовки не здатні прочитати асемблер EVM. Довіра була перекладена з юристів на аудиторів смарт-контрактів, які регулярно пропускали вразливості типу reentrancy або integer overflow.
3. **Абсолютизація багів:** Будь-який дефект у коді ставав легітимним правом хакера спустошити казначейство, оскільки система не знала поняття добросовісності або юридичної помилки.

### 1.2. Безпорадність цифрового паперу (DocuSign / Adobe Sign / PDF)
На іншому полюсі перебуває традиційний електронний документообіг:
1. **Інертний растр і текст:** PDF — це статичний цифровий відбиток, спроєктований у 1993 році для надсилання на лазерний принтер. Він не має внутрішньої здатності обчислювати, перевіряти вхідні умови чи реагувати на факти.
2. **Оренда довіри в SaaS:** Сучасний «цифровий підпис» у 99% випадків зводиться до централізованого сервісу (DocuSign, PandaDoc), який зберігає аудит-лог на своїх закритих серверах. Якщо SaaS зникне, зміниться чи зазнає витоку — доказова база розмивається.
3. **Дрейф реальності:** Договір декларує SLA (наприклад, доступність API 99.9% або компенсацію за затримку рейсу), але сам договір не може прийняти лог подій і детерміновано обчислити суму виплати. Для цього знову потрібні юристи, претензії, суди та нескінченні засідання.

### 1.3. Синтез Black-Heart: Самоверифікований Поліглот
Ми стверджуємо: **справжній договір повинен бути єдиним атомарним бінарним артефактом, що несе в собі одночасно людську мову, математичний предикат і механізм власної верифікації.**

$$\text{Document} = \mathbf{Prose} \oplus \mathbf{Predicate} \oplus \mathbf{Proof}$$

* Людина і суддя читають високоякісну типографіку в стандартному переглядачі PDF.
* Автоматизований агент або аудитор виконує `python3 agreement.pdf --facts log.json` і отримує детерміновану квитанцію Settlement `⚓`.

## 2. Фізична асиметрія бінарного формату: Письмо у два кінці

Як поєднати дві несумісні сутності — суворий синтаксис інтерпретатора (Python / WASM) та складну об'єктну структуру ISO 32000 PDF — в одному файлі без проміжних архівів чи zip-контейнерів?

Відповідь полягає в **протилежному напрямку зчитування** двох світів.

```text
БАЙТОВИЙ ПОТІК (Byte Stream):

[ Байт 0 ] --------------------------------------------------------> [ Байт N-1 ]
┌─────────────────────────┬────────────────────────────┬────────────────────────┐
│  ГОЛОВА (HEAD)          │  ТІЛО (BODY)               │  ХВІСТ (TAIL)          │
│  - Python Interpreter   │  - PDF Content Streams     │  - PDF Cross-Ref (xref)│
│  - Multi-line Docstring │  - Typography / Graphics   │  - PDF Trailer / Root  │
│  - Deterministic AST    │  - Embedded %🖤 Claims     │  - Python Standalone   │
│  - ATP Ledger / Hashes  │  - Neutral Oracle Caps     │    Runner Entrypoint   │
└─────────────────────────┴────────────────────────────┴────────────────────────┘
        │                                                      ▲
        │                                                      │
   Парсер коду                                           Парсер PDF
   (Зчитує зверху вниз)                                  (Зчитує знизу вгору)
```

### 2.1. Head-Seeking: Інтерпретатор коду
Інтерпретатори мов програмування читають файли **від зміщення 0 вперед**:
* Перший рядок може бути коментарем або визначенням кодування (`# coding: utf-8`).
* Другий рядок відкриває багаторядковий сировий літерал (`r"""%PDF-1.7...`), який поглинає весь бінарний графічний масив PDF без синтаксичних помилок.
* Для інтерпретатора весь PDF є просто константою, яку він тримає в пам'яті як власний вхідний текст.

### 2.2. Tail-Seeking: Парсер PDF (ISO 32000)
Двигуни візуалізації (macOS Quartz, Acrobat, PDFium, Chrome) читають файл **з кінця назад**:
* Парсер шукає маркер кінця файлу `%%EOF` в останніх 1024 байтах.
* Безпосередньо перед `%%EOF` розташоване зміщення `startxref <offset>`, яке вказує на точне положення таблиці об'єктів `xref`.
* Парсер завантажує словник `/Root` і рендерить сторінки, повністю ігноруючи будь-який байткод чи інтерпретатор, розташований за межами об'єктів.

### 2.3. Властивість непорушного сусідства
Ця асиметрія відкриває можливість **дуального письма**:
* Ми можемо нарощувати код і логіку від голови вниз,
* Ми можемо нарощувати візуальні об'єкти від хвоста вгору,
* А в середині вони зустрічаються у спільній точці синхронізації — коментарному блоці `%🖤`, де зашиті контентно-адресовані клейми та квитанції нормальної форми.

## 3. Літератна Монада та Подвійний Функтор (Literate Bifunctor Monad)

Традиційне літератне програмування (Дональд Кнут, WEB/CWEB) страждає від проблеми **одностороннього зносу (Documentation Drift)**:
програміст змінює код у танглі (tangle), але забуває оновити опис у віве (weave), або навпаки.

Щоб гарантувати 100% нерозривність коду та тексту, ми формалізуємо цей зв'язок як **літератну монаду**.

### 3.1. Означення стану
Монадичний контейнер $\mathcal{M}(A)$ визначається як трійка:

$$\mathcal{M}(A) = \langle S_{\text{comp}}, \; P_{\text{doc}}, \; A \rangle$$

де:
* **$S_{\text{comp}}$ (Computational Spine):** Детермінований стан обчислювального автомата:
  $$S = \langle \text{AST}, \; \text{ATP}_{\text{budget}}, \; \text{ATP}_{\text{spent}}, \; \text{Env} \rangle$$
* **$P_{\text{doc}}$ (Presentation Spine):** Ієрархічне дерево візуального макета документа:
  $$P = \langle \text{Nodes}, \; \text{Pages}, \; \text{Layout}, \; \text{VisualHash} \rangle$$
* **$A$:** Значення, повернуте поточною операцією.

### 3.2. Монадичні операції

#### 1. Чистий елемент (`unit` / `return`):
$$\textbf{unit}(x) = \langle S_0, \; P_0, \; x \rangle$$

#### 2. Зв'язування (`bind` / $\gg=$):
$$(\gg=) : \mathcal{M}(A) \to (A \to \mathcal{M}(B)) \to \mathcal{M}(B)$$

$$m \gg= f = \begin{pmatrix}
\text{нехай } \langle S_1, P_1, a \rangle = m \\
\text{нехай } \langle S_2, P_2, b \rangle = f(a) \\
\langle S_1 \oplus S_2, \; P_1 \cup P_2, \; b \rangle
\end{pmatrix}$$

Оператор $\oplus$ поєднує обчислювальні стани (зменшує залишковий ліміт ATP, акумулює журнал редукцій SKIY або предикатів).  
Оператор $\cup$ атомарно дописує до презентаційного дерева нові параграфи, формули чи таблиці фактів.

#### 3. Атомарний крок обчислення з авто-дописом (`step`):
$$\textbf{step}(\text{rule\_id}, \; \text{predicate}) : \mathcal{M}(\text{Receipt})$$
Ця операція виконує редукцію в $S$, спалює фіксовану кількість ATP, і **в тому ж такті** генерує в $P$ відповідний юридичний пункт та візуальний блок доказу:

$$\Delta S \iff \Delta P$$

**Інваріант анти-дрейфу:**  
У цій системі фізично неможливо змінити обчислення без автоматичного генерування нового тексту, і неможливо додати параграф у документ, не зв'язавши його з формальним предикатом.

## 4. Подвійні Дерева (Dual-Spine Trees): Гомоморфізм двох хребтів

Структурно самоверифікований документ спирається на два паралельні дерева:

```text
                  СПІЛЬНИЙ КОРІНЬ (JOINT ANCHOR)
                   H_dual = SHA-256(H_code || H_visual)
                                  │
         ┌────────────────────────┴────────────────────────┐
         ▼                                                 ▼
   [ ХРЕБЕТ КОДУ ]                                   [ ХРЕБЕТ ПРОЗИ ]
     (Code Spine)                                      (Visual Spine)
          │                                                 │
   ┌──────┴──────┐                                   ┌──────┴──────┐
   ▼             ▼                                   ▼             ▼
Clause #1     Clause #2                           Article 1     Article 2
 (Predicate)   (Predicate)                         (Heading)     (Heading)
   │             │                                   │             │
   ▼             ▼                                   ▼             ▼
SKI Term     Evidence Hash                        Paragraph    Receipt Box
```

### 4.1. Хребет Коду (Code Spine)
* **Вузли:** Комбінаторні вирази SKIY, булеві предикати над фактами, ліміти ATP, перевірки підписів.
* **Зв'язки:** Залежності між умовами (наприклад: *«Пункт 3.2 набирає чинності лише якщо Пункт 2.1 визнано порушеним»*).
* **Хеш стану:** Детермінований Merkle-хеш усіх визначених правил та їхніх нормальних форм:
  $$H_{\text{code}} = \text{MerkleRoot}(\{\text{Rule}_i, \text{Expr}_i, \text{Expected}_i\})$$

### 4.2. Хребет Прози (Visual Spine)
* **Вузли:** Сторінки (Pages), розділи (Sections), юридичні статті (Articles), текстові блоки, шрифтові набори, розмітка таблиць.
* **Хеш макета:** Канонічний хеш візуального потоку об'єктів PDF:
  $$H_{\text{visual}} = \text{SHA-256}(\text{PDF\_Catalog} \mathbin{\Vert} \text{PageObjects})$$

### 4.3. Спільний Якір Довіри (Joint Anchor)
Цілісність документа фіксується одним 32-байтовим числом:
$$H_{\text{dual}} = \text{SHA-256}(H_{\text{code}} \mathbin{\Vert} H_{\text{visual}})$$

* Якщо зловмисник спробує змінити текст параграфа в PDF-редакторі (наприклад, змінити суму з «100 000 USD» на «10 000 USD»), змінюється $H_{\text{visual}}$ і зміщення в `xref`. При спробі виконання `python3 document.pdf` рантайм негайно виявляє підробку та блокує settlement (`[✗ RED] TAMPER DETECTED`).
* Якщо зловмисник спробує підправити логіку перевірки в Python-скрипті, змінюється $H_{\text{code}}$, порушуючи зв'язок із вбудованим коментарем `%🖤`.

## 5. Самоверифіковані Договори (Proof-Bearing Contracts)

Переведемо цю теорію в прикладну площину юриспруденції та розробки систем.

### 5.1. Анатомія договору нового типу
Самоверифікований договір (наприклад, угода про рівень обслуговування — Service Level Agreement, SLA) складається з трьох шарів:

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        ЮРИДИЧНА ПРЕАМБУЛА                              │
│   Ця Угода укладена між ТОВ «Провайдер» та ТОВ «Клієнт» про надання    │
│   хмарних послуг. Мова договору: українська. Право: матеріальне право. │
├────────────────────────────────────────────────────────────────────────┤
│                     ФОРМАЛІЗОВАНИЙ ПРЕДИКАТ                            │
│   Стаття 4.1 (Гарантована доступність):                                │
│     Uptime >= 99.5% за календарний місяць.                             │
│   Стаття 4.2 (Штрафні санкції):                                        │
│     За кожні повні 0.1% нижче норми нараховується штраф 500 USD.       │
│                                                                        │
│   [ Embedded Predicate: calc_penalty(uptime_pct, base_cost) ]          │
├────────────────────────────────────────────────────────────────────────┤
│                     ДОКАЗОВИЙ ПАКЕТ (EVIDENCE)                         │
│   Інцидент #1: 2026-09-02 (Таймаут шлюзу: 180 хв). Хеш: a1c4e9...     │
│   Інцидент #2: 2026-09-05 (Збій живлення: 120 хв). Хеш: f83d10...     │
│   Всього простою: 300 хв. Загальний час: 43200 хв. Uptime: 99.305%     │
├────────────────────────────────────────────────────────────────────────┤
│                     ВЕРДИКТ ТА КВИТАНЦІЯ (SETTLEMENT)                  │
│   ⚓ SETTLED: BREACH CONFIRMED                                          │
│   Penalty Due: 1000 USD | ATP: 42 | Digest: 7e2a9b40f1                │
└────────────────────────────────────────────────────────────────────────┘
```

### 5.2. Процедура розгляду та виконання
1. **Підписання:** Обидві сторони підписують файл за допомогою криптографічних ключів (ed25519 або GPG). Їхні підписи вбудовуються у візуальний блок PDF і коментарний блок коду.
2. **Моніторинг:** Протягом дії договору події фіксуються у форматі доказових капсул (згідно зі специфікацією `warrant` / `CHORD-CAPSULE-0.1`).
3. **Виконання вердикту:**
   Наприкінці місяця бухгалтер, фінансовий бот або судовий виконавець виконує:
   ```bash
   python3 service_agreement.pdf --adjudicate
   ```
   Файл відкриває сам себе, перевіряє власний спільний корінь $H_{\text{dual}}$, виконує детермінований предикат над фактами інцидентів і друкує юридично чинний сертифікат врегулювання.

Жодного звернення до сторонніх хмар, жодної залежності від DocuSign, жодної можливості «загубити логи».

## 6. Інтеграція в екосистему: Radicle, Warrant та Sigma-Glyph

Ця архітектура органічно замикає загальну конструкцію проєктів екосистеми:

1. **Radicle Transport (`triad_delivery.py`):**
   * **Поверхня обговорення (Surface of Deliberation):** чернетки, пропозиції умов, дипломатичні торги ведуться в Radicle COBs (`refs/cobs/`).
   * **Поверхня результату (Surface of Result):** у репозиторій фіксується виключно фінальний бінарний поліглот `agreement.pdf` без зайвого історичного шуму.
2. **Warrant Engine (`warrant`):**
   * Постачає доказовий пакет (Evidence Pack).
   * Автономні модельні судді (Gemini Flash, Mistral Large) можуть проводити пре-аудит фактів, але фінальне карбування квитанції `⚓` виконує суто математичний Black Cone.
3. **Sigma-Glyph (`glyph.py`):**
   * Забезпечує фундаментальний детермінований рантайм на чистих комбінаторах UTF-8 без жодних зовнішніх залежностей.
