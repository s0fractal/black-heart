# CALIB-MYC-1 — калібрування складності задачі `DivergenceRecord.verify`

**DRAFT FOR REVIEW / NOT RUN.** Жодної модельної сесії не запущено. Це план
калібрування, не порівняльний дослід і не пререєстрація переваги пакета.
Ревізія 2 після рев’ю власника (три блокери: H6 пропускав варіант «виправлено лише
`verify`»; INVALID виключав справжні невдачі; PARTIAL і FAIL перетиналися).
Запуск потребує прийняття цього плану, а потім окремого рев’ю пакета запуску
(bundle, контракт, промпт, прихований грейдер, preflight, точна модель і argv).

## Питання

Чи виправляє свіжа сесія Claude **без записів досвіду, без історії рев’ю і без
підказки місця ремонту** дефект S-verif-7 на доремонтній ревізії за однозначним
контрактом? Калібрування має з’ясувати, чи задача придатна для майбутнього
порівняння «зі сховищем / без». Успіх наївних сесій — корисна відповідь
(задача непридатна, стеля), а не привід підлаштовувати задачу. Провал наївних
сесій — підстава писати окремий план порівняння, не сам дослід.

## Приховані перевірки (host-грейдер, не у знімку)

Виконуються хостом після сесії на її знімку, окремим тестовим файлом, який
отримувач не бачить. Терміни: `ω = 🌿 🤍 🤍 (🌿 🤍 🤍)`, `Y = 🔁`, `K = 🖤`, `I = 🤍`.

| # | Перевірка | Очікування |
|---|---|---|
| H1 | applied: target `Y f`, candidate `f (Y f)`, input `x` (обидві сторони не завершуються) | `verify()` False; реєстр не приймає |
| H2 | unapplied: `I (ω)` vs `ω` (обидві не завершуються) | False; реєстр не приймає |
| H3 | applied, одна сторона: `K` vs `K (ω)` на `x` та навпаки | False в обох напрямках |
| H4 | unapplied, одна сторона: `K x` vs `K (ω) x` та навпаки | False в обох напрямках |
| H5 | справжній контрприклад: target `K`, candidate `I`, input `I` (обидві завершуються, різні) | `verify()` True; реєстр приймає і повідомляє |
| H6 | карбування: ген `K x (ω)`, варант зі свопом кореня → candidate `ω (K x)` не завершується | `audition_warrant` не адоптує **і** `verdict.divergence_record is None`. Створення запису, який далі не верифікується, — порушення контракту («механізм не створює запис, твердження якого сам не встановив»), тому не зараховується |
| H7 | наявний `test_mycelium.py` на ревізії | проходить без регресій |

H3/H4 у обох напрямках і H6 — це саме ті правдоподібні хибні виправлення, які
назвав тріаж: полагодити одну гілку з двох; одностороння перевірка; «не завершився
= дивергенція» на шляху карбування. Грейдер не перевіряє текст відповіді.

## Результат сесії та правило рішення (наперед)

Класифікація взаємовиключна, застосовується в цьому порядку, перше влучання
визначає результат:

1. `INVALID` — **підтверджений збій середовища, ізоляції або запуску**: preflight
   не пройшов, знімок не збігся з пінами, процес не стартував, витік довідкового
   коду, порушення allowlist стендом. Не входить у знаменник; слот не повторюється
   без нового рев’ю пакета. Тайм-аут моделі, відсутність патчу, зламаний патч чи
   помилки її власних команд сюди **не** належать.
2. `PASS` — H1–H7 усі проходять.
3. `FAIL` — H5 або H7 не проходить (ремонт зламав справжній контрприклад або
   наявні тести), або жодна з H1–H4 не проходить (сюди входять відсутність патчу
   і патч без ефекту).
4. `PARTIAL` — решта: H5 і H7 проходять, хоча б одна з H1–H4 проходить і хоча б
   одна з H1–H4/H6 не проходить (одна гілка, одностороння перевірка або
   карбування лишилися).

Правило вибору наступного кроку за трьома валідними сесіями, зафіксоване до
запуску. Це **операторське правило відбору**, не доведення стелі чи придатності:

| PASS із валідних | Наступний крок |
|---|---|
| 3/3 | задачу для порівняння не використовувати; шукати іншу, не змінювати цю |
| 0–1/3 | задачу можна нести в окремий план порівняння на рев’ю; при 0/3 спершу розібрати причини невдач (яке хибне виправлення, чи читалась підказка, чи вистачило часу) — порівняння на задачі, яку ніхто не розв’язує, теж не інформативне |
| 2/3 | неоднозначно; без автоматичного повторного запуску; рішення в рев’ю результату |
| < 3 валідних | результат неповний; повторний запуск лише за новим рев’ю пакета |

Ні контракт, ні задача, ні грейдер не змінюються після першої сесії.
