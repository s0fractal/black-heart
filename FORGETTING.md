## 1. Преамбула: Чому накопичення без забування вбиває організм

У специфікації [WARRANT.md](WARRANT.md) встановлено сувору дисципліну розрізнення ґатунків свідчення (∅, G, A, E, C). Однак будь-яка жива система, здатна накопичувати знання без обмеження, стикається з когнітивним колапсом:
1. **Аритмія метаболізму:** Зростання активного простору пошуку споживає дедалі більше ATP газу на перевірку застарілих або відкинутих гіпотез.
2. **Метушня (Vanity Churning):** Генерація тривіальних контрприкладів (ґатунок C) із нульовою семантичною цінністю заради отримання винагороди.
3. **Хибна дихотомія між знищенням та вічною пам'яттю:** Традиційні бази даних обирають між необоротним видаленням (`DELETE FROM`) або безконтрольним роздуванням індексів.

`CONTROLLED-FORGETTING-0.1` впроваджує третій шлях: **Епістемічне забування як зміна політики допуску (Admission Gate Policy), а не знищення історичних байтів (History Erasure).**

## 2. Головний принцип: Допуск проти Стирання

```
+-------------------------------------------------------------------------+
|                  ІСТОРИЧНИЙ СУБСТРАТ (HISTORICAL SUBSTRATE)             |
|       100% збереження в байтах ISO 32000 PDF / Git CAS / IPFS DAG       |
|                                                                         |
|   [Архівний алель]     [Спростована гіпотеза]     [Застаріла еврика]    |
|   (Tombstone #1)        (Tombstone #2, REFUTED)     (Tombstone #3)       |
+-------------------------------------------------------------------------+
                                   |
                          [ResurrectionGuard]
                     (Інваріант I3: Gatekeeper)
                                   |
                                   v  (Тільки через підписаний ReAdoptionRecord)
+-------------------------------------------------------------------------+
|                  АКТИВНА ПОВЕРХНЯ (ACTIVE EVALUATION SURFACE)           |
|               Бере участь в обчисленнях, витрачає ATP газ               |
|                                                                         |
|        [Axiomatic Rules]     [Grounded Reductions]     [Active E]       |
+-------------------------------------------------------------------------+
```

1. **Історичний субстрат (Historical Substrate):** Всі раніше висунуті алелі, твердження та вердикти назавжди зберігаються у криптографічному та байтовому літописі документа. Жоден байт минулого не модифікується (відповідно до інваріанта ISO 32000 §7.5.6).
2. **Активна поверхня (Active Evaluation Surface):** Підмножина знань, що автоматично завантажується локальним оцінювачем (`Local Immune Evaluator`), бере участь у схрещуванні організмів і споживає газ метаболізму ATP.
3. **Забування = Екскомунікація з активної поверхні:** Ретирування артефакту переводить його зі статусу `ACTIVE` у статус `RETIRED`. Він перестає витрачати ресурс, але залишається доступним для ретроспективного аудиту та історичного аналізу.

## 3. Нормативні Інваріанти I1–I8 (CONTROLLED-FORGETTING-0.1)

Кожна операція забування в Project Black-Heart підпорядковується восьми непорушним інваріантам:

### Інваріант I1: Точний суб'єкт (Exact Subject)
Ретирування адресує виключно конкретний артефакт або ребро, ідентифіковане контентним криптографічним дайджестом (SHA-256) та точним ID.  
*Заборонено розпливчасті або шаблонні директиви на кшталт «забути всі гіпотези про комутативність».*

### Інваріант I2: Виключення за замовчуванням (Default Exclusion)
Ретирований артефакт безумовно виключається з активної поверхні оцінювача. Метаболічний цикл ігнорує його без виклику винятків чи аварійних зупинок.

### Інваріант I3: Заборона неявного воскресіння (No Implicit Resurrection)
Наявність артефакту в історичних байтах файлу ніколи не дає права автоматично завантажити його в активну пам'ять.  
Спроба виконати або долучити ретирований артефакт без дійсного `ReAdoptionRecord` блокується імунним бар'єром `ResurrectionGuard` із викидом `EpistemicResurrectionError`.

### Інваріант I4: Втрата є першокласною сутністю (Loss is First-Class)
Кожен запис про ретирування (`RetirementRecord`) **МУСИТЬ** містити непорожнє поле `loss_declaration`.  
Система вимагає від автора формального визнання того, що саме втрачається при ретируванні (наприклад: *«Втрачено експериментальну історію неоптимального схрещування; звужено горизонт пошуку в підпросторі swap»*).  
*Спроба зареєструвати ретирування з порожнім або пробільним `loss_declaration` викидає `ValueError`.*

### Інваріант I5: Ретирування не є спростуванням (Retirement is Not Refutation)
Виведення артефакту з активної поверхні не змінює його математичної істинності. Твердження залишається таким, яким воно було зафіксоване.  
Лише режим `REFUTED` із пред'явленням валідного контрприкладу ґатунку C стверджує хибність. Режими `SUPERSEDED`, `ARCHIVED`, `WITHDRAWN`, `DEPRECATED` фіксують зміну прагматики або піднесення до сильнішої форми ($E \to A$), а не спростування.

### Інваріант I6: Криптографічна авторитетність (Cryptographic Authority)
Кожен `RetirementRecord` та `ReAdoptionRecord` має бути канонічно серіалізований (RFC 8785 JCS) і підписаний асиметричним ключем автора за протоколом RFC 8032 Ed25519 із доменним префіксом `retirement-sig-v1:` або `readoption-sig-v1:`.

### Інваріант I7: Непорушність байтів літопису (CAS & PDF Byte Preservation)
Ретирування не може перезаписувати наявні байти файлу чи літопису. Воно здійснюється виключно через інкрементне додавання (append-only) нових об'єктів та стели до тіла поліглота.

### Інваріант I8: Нетранзитивність композиції (Non-Transitive Composition)
Ретирування одного твердження $P$ у суперечливій системі тверджень $\{P, Q\}$ не робить автоматично істинним або валідним твердження $Q$. Допуск кожного збереженого твердження перевіряється незалежно.

|---|---|---|---|
| **`REFUTED`** | Спростовано конкретним контрприкладом (ґатунок C). Твердження хибне. | Свідок контрприкладу з операндами | **Багряний (Crimson)** `#E63340` |
| **`SUPERSEDED`** | Замінено підвищеним або сильнішим правилом ($E \to A$). | Обов'язковий непорожній `replacement_id` | **Золотий (Gold)** `#D9A626` |

| **`WITHDRAWN`** | Відкликано автором через виявлений дефект до формального C. | Обґрунтування відкликання | **Сланцевий (Slate)** `#808C99` |
| **`ARCHIVED`** | Історична віха; виключено з активної генерації для економії ATP. | Фіксація епохи архівації | **Темно-сірий (Dark Slate)** `#505A66` |
| **`QUARANTINED`** | Тимчасово ізольовано під час арбітражу або підозри на атаку. | Посилання на інцидент аудиту | **Бурштиновий (Amber)** `#E68A2E` |

## 5. Негативний простір: Міра $\mu(C)$ та метаболічна винагорода

### 5.1. Чому контрприклад без міри породжує метушню (Open Question 3)
У [WARRANT.md](WARRANT.md) §9.3 сформульовано фундаментальну проблему: якщо система винагороджує будь-яке ребро ґатунку C фіксованою премією, агенти мотивовані продукувати тривіальні контрприклади (наприклад, $0 \ne 1$, $0 \ne 2$, $0 \ne 3$), які викреслюють лише поодинокі ізольовані точки, не зменшуючи простір невизначеності.

### 5.2. Формальне визначення міри $\mu(C)$
Міра покриття негативного простору $\mu(C) \in [0.0, 1.0]$ визначає частку дерева виразів чи комбінаторного простору, яка усувається внаслідок прийняття контрприкладу або ретирування правила:

$$\mu(C) = 1.0 - \left(\frac{1}{2}\right)^{\frac{1}{\text{tree\_size}(\text{Pattern})}}$$

- **Широкі структурні спростування:**  
  Спростування симетрії $x\,y \to y\,x$ у некомутативній системі усуває понад $75\%$ невалідних перестановок ($\mu(C) = 0.75$).
- **Колапс констант:**  
  Спростування схлопування довільного терма $x$ в $I$ дає $\mu(C) = 0.65$.
- **Глибокі вузькі мутації:**  
  Усунення одиничного граничного випадку в глибокому піддереві отримує базову міру $\mu(C) \in [0.10, 0.25]$.

### 5.3. Метаболічна винагорода ATP
Організм, що ретирує неефективний або спростований алель, отримує повернення метаболічного палива ATP, яке вивільняється завдяки відсіканню мертвої гілки пошуку:

$$\text{Gas}_{\text{reclaimed}} = \text{base\_atp} + \lfloor 200 \times \mu(C) \rfloor$$

Це стимулює імунну систему шукати найбільш загальні спростування та очищувати активну поверхню.

## 6. Протокол повторного усиновлення (Re-Adoption Protocol)

Відповідно до Інваріанта I3, ретирований суб'єкт не може бути повернутий до активного стану автоматично.  
Якщо подальші дослідження або зміна аксіоматичного контексту доводять, що ретирування було надмірним або що знайдено репараційний доказ, оформлюється `ReAdoptionRecord`:

```text
ReAdoptionRecord := ⟨
    record_id:              SHA-256(canonical_jcs(body)),
    target_id:              ID суб'єкта, що повертається,
    retirement_record_id:   ID вихідного надгробка (Tombstone),
    new_evidence_claim_id:  ID нового свідчення, що реабілітує артефакт,
    justification:          Непорожнє епістемічне обґрунтування,
    author_pk_hex:          Публічний ключ ініціатора,
    signature_hex:          Ed25519-підпис над "readoption-sig-v1:<record_id>"
⟩
```

Після верифікації підпису та внесення запису в реєстр статус суб'єкта змінюється з `RETIRED` на `READOPTED`, і `ResurrectionGuard` знову дозволяє його допуск до активної поверхні.

## 7. Архітектура візуальних стел ISO 32000 (Tombstone Stele)

За стандартом ISO 32000 §7.5.6, кожна операція ретирування:
1. **Зберігає байтовий префікс вихідного поліглота:**
   $$\text{OutputBytes}[:\text{len}(\text{SourceBytes})] \equiv \text{SourceBytes}$$
2. **Додає візуальну сторінку-стелу (Tombstone Stele):**
   - Контрастне обсидіанове тло (`#0A0D12`).
   - Колір рамки картки, що чітко сигналізує причину ретирування (багряний для REFUTED, золотий для SUPERSEDED, фіолетовий для DEPRECATED тощо).
   - Відображення обов'язкової декларації втрати (Invariant I4) та розрахованої міри $\mu(C)$.
3. **Оновлює каталог сторінок (`/Type /Pages`):**
   - Перевипускає об'єкт 2 з доданим посиланням у масив `/Kids` та збільшеним `/Count`.
4. **Вбудовує канонічний JSON-маніфест:**
   `# %🖤 RETIREMENT_MANIFEST: {"tombstones": {...}, "readoptions": {...}}`
5. **Вбудовує автономний Python-аудитор:**
   Документ залишається самовиконуваним скриптом:
   ```bash
   python3 document.pdf
   ```
   який без зовнішніх залежностей перевіряє криптографічні підписи всіх наявних надгробків та стан імунних шлюзів.

## 8. CLI Інтерфейс

Рушій інтегровано в єдиний CLI-інтерфейс проекту Black-Heart:

```bash
# Ретирувати алель або правило з декларацією втрати:
python3 cli.py warrant-forget retire RULE_SWAP_01 e3b0c44298... \
    -m REFUTED \
    -l "Pruned non-confluent swap rule that broke normal form invariance." \
    --rule "x y -> y x" \
    -o my_organism.pdf

# Аудіювати стан надгробків та перевірити підписи в поліглоті:
python3 cli.py warrant-forget audit my_organism.pdf

# Відобразити активну поверхню проти підрізаного негативного простору:
python3 cli.py warrant-forget surface my_organism.pdf

# Авторизувати повторне усиновлення суб'єкта за наявності нового доказу:
python3 cli.py warrant-forget readopt my_organism.pdf RULE_SWAP_01 \
    --reason "Refactored rewrite system with commuting confluence proof." \
    --evidence "CLAIM_RESTORED_E01"
```
