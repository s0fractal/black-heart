## 1. Проблема Ізольованого Документа

У попередніх специфікаціях (`MONAD.md`, `GENOME.md`) кожен документ розглядався як автономний мікрокосм:
він сам несе свої клейми, сам себе верифікує і сам редукує факти.

Проте в реальному світі зобов'язання завжди **двосторонні або багатосторонні**:
1. **Розрив між декларацією та фактами:** Договір декларує правила SLA, але фактами аварій або простою володіє незалежний третій суб'єкт — моніторинговий оракул (Cloudflare, Datadog, AWS, авіадиспетчерська служба Eurocontrol).
2. **Ризик підробки фактів однією зі сторін:** Якщо клієнт сам вписує логи в договір — провайдер не вірить; якщо провайдер сам заповнює звіт — клієнт підозрює приховування інцидентів.
3. **Криза наукової відтворюваності:** Дослідницькі статті дають посилання на репозиторії GitHub, які за 2–5 років зникають (404 Not Found), ламаються через несумісність версій або видаляються авторами.

## 2. Двосторонній Міждокументний Протокол (Bilateral Interlocking)

Замість того, щоб звертатися до централізованого SaaS або платити комісії в блокчейні, дві сторони обмінюються **двома взаємопов'язаними поліглот-документами**:

```text
┌──────────────────────────────────────────────────┐        ┌──────────────────────────────────────────────────┐
│      ДОКУМЕНТ А: ДОГОВІР КЛІЄНТА                 │        │      ДОКУМЕНТ В: ЗВІТ ОРАКУЛА                    │
│      (Client SLA Agreement Polyglot)             │        │      (Provider / Oracle Telemetry Polyglot)      │
│                                                  │        │                                                  │
│   - Юридичний текст SLA: Uptime >= 99.5%        │        │   - Оракул: Datadog Cloud Telemetry              │
│   - Формула штрафу: $500 за 0.1% простою         │        │   - Журнал зафіксованих збоїв (INC-01, INC-02)   │
│   - Довірений публічний ключ Оракула: PK_oracle  │        │   - Час простою: 300 хв (Uptime: 99.306%)        │
│   - Спільний якір договору: H_contract           │        │   - Підпис Ed25519 Оракула: Sig_oracle           │
│   - Підпис Сторін А і Б: Sig_parties             │        │   - Спільний якір оракула: H_oracle              │
└────────────────────────┬─────────────────────────┘        └────────────────────────┬─────────────────────────┘
                         │                                                           │
                         └─────────────────────────┬─────────────────────────────────┘
                                                   │
                                     ВЗАЄМНЕ ЗАМИКАННЯ (INTERLOCKING)
                                                   │
                                                   ▼
                         ┌───────────────────────────────────────────────────────────┐
                         │              ДВОСТОРОННІЙ ВЕРДИКТ (SETTLEMENT)            │
                         │   python3 agreement.pdf --adjudicate-with telemetry.pdf   │
                         │                                                           │
                         │   1. Перевірка цілісності обох файлів (ISO 32000 xref)    │
                         │   2. Верифікація Sig_oracle через PK_oracle               │
                         │   3. Витяг фактів телеметрії з Document B                 │
                         │   4. Редукція предикату договору Document A               │
                         │   5. Карбування двосторонньої квитанції:                  │
                         │      ⚓ SETTLED: SLA BREACH CONFIRMED ($500 USD)          │
                         │      Joint Digest: SHA-256(H_contract || H_oracle)        │
                         └───────────────────────────────────────────────────────────┘
```

## 3. Криптографічний Механізм Замикання

### 3.1. Схема Довіри без Посередників
1. Документ А фіксує у своєму геномі / маніфесті умову:
   $$\text{ExpectedOraclePK} = \text{PK}_{\text{oracle}}$$
2. Коли Документ А запускається з параметром `--adjudicate-with telemetry.pdf`:
   * Він відкриває бінарний потік `telemetry.pdf`.
   * Зчитує з нього `manifest` оракула.
   * Перевіряє підпис оракула:
     $$\textbf{verify}(\text{PK}_{\text{oracle}}, \; \text{CanonicalBytes}(\text{TelemetryData}), \; \text{Sig}_{\text{oracle}}) \stackrel{?}{=} \textbf{True}$$
   * Якщо підпис недійсний або ключ не збігається — розгляд негайно блокується:
     `[✗ UNTRUSTED ORACLE] Telemetry signature rejected!`
   * Якщо підпис справжній — факти інцидентів передаються в числюваний предикат договору.

### 3.2. Спільний Свідок Врегулювання (Bilateral Witness Anchor)
Результат врегулювання закріплюється спільним Merkle-хешем:
$$H_{\text{bilateral}} = \text{SHA-256}(H_{\text{agreement\_anchor}} \mathbin{\Vert} H_{\text{oracle\_anchor}} \mathbin{\Vert} \text{VerdictReceipt})$$

Цей 32-байтовий хеш фіксує обидва документи одночасно:
жодна сторона не може замінити свій файл або заявити, що розрахунок проводився за іншою версією телеметрії.

## 4. Вбудовані Сховища Коду (ISO 32000 Embedded Code Vaults)

Щоб гарантувати абсолютну відтворюваність будь-якого наукового паперу, доказу чи юридичного договору через 50 років, документ повинен містити в собі середовище власного виконання.

### 4.1. Специфікація ISO 32000-1 §7.7.4
Стандарт PDF передбачає тип об'єкта `/EmbeddedFile`.
У словник документа `/Root` додається структура імен:
```text
/Names <<
  /EmbeddedFiles <<
    /Names [(source_code.tar.gz) 12 0 R]
  >>
>>
```
Об'єкт `12 0 obj` містить компресований або сировий tar-архів із повним вихідним кодом проекту, тестами та детермінованим `lock`-файлом залежностей.

### 4.2. Автономне Розпакування
Будь-який суб'єкт (людина чи CI/CD пайплайн) може виконати:
```bash
python3 document.pdf --unpack-vault [output_dir]
```
Файл читає власний PDF-потік, знаходить об'єкт вбудованого сховища, перевіряє його контрольний хеш SHA-256 і розгортає повний робочий простір.

**Наукова стаття чи контракт стають непорушним ковчегом істини (Self-Preserving Archive).**
