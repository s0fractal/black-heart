# Чернетка контракту назв і адрес Black-Heart

Статус: **DRAFT — для обговорення, не запроваджений стандарт**.
Дата: 2026-09-13.
Підстава: розмова про 16 інженерних поверхів, стабільні адреси документації
та README як індекс. Назви поверхів і схема розподілу нижче — пропозиція.

Цей документ сам поки не отримує адресу: це уникає самопризначення нового
стандарту чинним. Прийняття контракту і міграція файлів — окремі зміни.

## 1. Мета та область

Кожен документ має стабільну адресу, зрозумілу назву й визначену область
відповідальності. Статуси, обмеження й терміни мають одне основне місце
опису; інші документи посилаються на нього.

16 поверхів — класифікація інженерних областей. Їхні номери не означають
зрілості, пріоритету, сили доказу або обов'язкового порядку реалізації.
Залежності між поверхами записуються явно й можуть утворювати граф.

Контракт стосується насамперед Markdown-документації. Він не змінює
Python-імпорти, імена CLI-команд, схеми підписаних повідомлень, ідентифікатори
claims, адреси PDF чи формати експериментальних артефактів.

## 2. Адреса

Повна адреса має форму `xHNNN`:

- `x` — буквальний нижній латинський символ, маркер адреси проєкту;
- `H` — одна шістнадцяткова цифра поверху: `0`–`9`, `A`–`F`;
- `NNN` — три шістнадцяткові цифри документа всередині поверху;
- усі літери hex у канонічній адресі — великі; рівно чотири цифри після `x`.

Діапазон: `x0000`–`xFFFF`: 16 поверхів, по 4096 адрес у кожному.
Адреса документа відповідає виразу `^x[0-9A-F]{4}$`.

`x8` — коротке позначення поверху в тексті, а не адреса документа.
`x8000` — його головний документ. `xA000` належить поверху 10;
`x1000` — поверху 1. Префікс `0x` тут не використовується.

Адреса позначає предмет документа, а не його версію, файловий шлях чи хеш.
Для точного історичного стану потрібні також Git commit і шлях; для перевірки
байтів артефакту — відповідний дайджест. Адреса `x8001` їх не замінює.

## 3. Ім'я файла

Форма для нового адресованого документа:

```text
xHNNN-short-descriptive-name.md
```

Граматика: `^x[0-9A-F]{4}-[a-z0-9]+(?:-[a-z0-9]+)*\.md$`.

- Адресу від назви відділяє один дефіс `-`.
- Назва — коротка, описова, англійська ASCII, нижній регістр, слова через дефіс.
- Заголовок і текст документа можуть бути українською або іншою мовою.
- Статус, відсоток готовності, дата й номер редакції не кодуються в імені.
- `final`, `latest`, `new`, `v2` не використовуються як спосіб вибору чинної копії.

Приклади можливих назв (ще не призначені адреси):

```text
x8000-document-interface.md
x8001-roadmap.md
x8002-boundaries.md
x8003-terminology.md
x8010-cli-contract.md
x8011-transition-publication.md
```

`_` резервується для позначення невідомого в робочому тексті:
`x8___` — поверх відомий, адреса документа не призначена;
`x____` — адреса не визначена. Це placeholders, не адреси, не шаблони пошуку
і не допустимі імена опублікованих документів. Конкретний пропуск усередині
номера, наприклад `x80_1`, не створює частково чинної адреси.

Це резервування не поширюється на наявні імена коду: `library_interaction.py`
та інші Python-модулі з `_` зберігають свої назви.

## 5. Розподіл адрес усередині поверху

Пропонується однакове резервування для кожного `H`:

| Адреса | Призначення |
| --- | --- |
| `xH000` | Головний контракт та індекс поверху |
| `xH001` | Роадмап: наступні кроки, залежності, критерії приймання |
| `xH002` | Обмеження, невирішені питання, межі перевірених тверджень |
| `xH003` | Терміни та їхнє походження |
| `xH004`–`xH00F` | Резерв; значення не призначено |
| `xH010`–`xHFFF` | Тематичні контракти, описи компонентів та інші документи |

`H` у цій таблиці — метазмінна, не допустима hex-цифра.
Не потрібно створювати порожні файли для всіх резервів. Поки окремого
документа немає, відповідні розділи живуть у `xH000`. Після винесення
головний документ лишає посилання, а не другу нормативну копію.

Адреси призначаються в окремому реєстрі `ADDRESS-INDEX.md` (у корені проєкту) як чернетковому реєстрі. Він створений разом із пілотними документами;
його рядки не означають автоматичного прийняття контрактів.
Рядок реєстру містить адресу, шлях, назву, стан документа і, за потреби,
посилання на наступника. У межах репозиторію одна адреса має один основний
документ. Конфлікти призначення розв'язуються до злиття змін.

## 6. Обов'язковий контракт документа

Адресований документ починається з метаданих; приклад:

```yaml
---
id: x8010
status: draft
scope: CLI argument and output contract
introduced_by: pending
supersedes: []
superseded_by: []
---
```

`introduced_by` — посилання на PR або наявний запис про прийняття; тут
допустиме `pending`, доки такого запису немає. Хеш власного майбутнього
коміту в документ не вбудовується.

Стани документа: `draft`, `active`, `superseded`, `withdrawn`.
`active` означає чинність опису/контракту, а не завершеність реалізації.
Рішення про прийняття фіксується в рев'ю; сама наявність файла не робить
чернетку чинним контрактом.

Для головного документа поверху потрібні:

1. Предмет і виключення з області.
2. Входи, виходи, передумови, названі відмови та інваріанти.
3. Основні документи й залежності від інших поверхів.
4. Посилання на реальні модулі, CLI та тести.
5. Стан реалізації й перевірок із конкретною ревізією, коли йдеться про вимір.
6. Обмеження та наступні кроки з критеріями приймання.
7. Терміни: вихідне значення, джерело, локальне застосування та відмінності.

Спеціалізований документ посилається на головний контракт і деталізує свій
предмет. Не потрібно механічно дублювати всі сім розділів у кожному файлі.

Термінологічний запис розрізняє формальне визначення, інженерне наближення
та метафору. Невідоме походження позначається як невідоме; історія терміна
не вигадується для заповнення розділу. Назва «суверенний», «герметичний»
або «підтверджений» має посилатися на конкретну перевірювану властивість.

## 7. README та захист від дрейфу

Кореневий README містить коротке призначення проєкту, мінімальний перевірений
приклад входу й індекс поверхів/реєстру. Докладні контракти, роадмапи та
мінливі результати тестів живуть у своїх основних документах.

- Один нормативний факт має одне основне місце; решта посилається на нього.
- Число тестів або вердикт рев'ю має ревізію й область, а не статус «назавжди».
- Зміна поведінки включає оновлення відповідного контракту або явну позначку
  розходження; нова назва не приховує невирішений дефект.
- Індекс веде до файла звичайним відносним Markdown-посиланням. Голий `x8010`
  допомагає пошуку, але не припускає існування автоматичного resolver-а.
- Перевірка назв і посилань може бути автоматизована пізніше. Вона не доводить
  відповідності тексту коду; це окрема задача рев'ю й поведінкових контролів.

## 8. Зміни назв, перенесення та історія

Адреса не перевикористовується для іншого предмета після її прийняття.
Редакція того самого контракту зберігає адресу; історичну редакцію визначає
Git commit. Несумісну зміну публічного профілю додатково версіонують у самому
протоколі — адреса документа не замінює версію wire format.

Перейменування описового суфікса потребує оновлення реєстру й посилань.
За наявності зовнішніх посилань старий шлях лишає короткий покажчик на новий.
Якщо предмет переноситься на інший поверх або розділяється, нові документи
отримують нові адреси, а стара лишається зі станом `superseded` і посиланнями.
Відкликана адреса також не повертається у вільний пул.

Заморожені протоколи, пре-реєстрації, підписані записи, пакети експериментів
і вже опубліковані артефакти не переписуються заради нового неймінгу.
Їх можна адресувати через новий індексний документ, що посилається на
історичний шлях та ревізію; сам історичний файл не перейменовується автоматично.

## 9. Поступове запровадження: кореневий каталог і пласка структура

Нормативні адресовані документи (`xHNNN-*.md`) живуть **прямо в кореневому каталозі репозиторію**
поруч із модулями коду (відповідає пласкій структурі Black-Heart; підкаталоги `x0/`–`xF/` не створюються).
Каталог `docs/` зберігається для історичних журналів, леджерів ремонту (`REMEDIATION-LEDGER.md`),
спеціалізованих протоколів експериментів та пропозицій (`docs/proposals/`).


Послідовність після прийняття:

1. Скласти карту «наявний документ → предмет → запропонована адреса»,
   позначивши дублікати, суперечності та історичні незмінні матеріали.
2. Створити реєстр і лише потрібні головні документи поверхів.
3. Переносити чинні описи малими змінами з оновленням посилань. Старий шлях
   за потреби лишає покажчик; історичні джерела лишаються історичними.
4. Скоротити README до входу й індексу після появи робочих цільових посилань.
5. Додати перевірку унікальності адрес, граматики назв, відповідності `id`
   префіксу файла та відсутності битих посилань.

Наявний `DOCUMENTATION-ROADMAP.md` — вхідний матеріал для карти, не автоматично
встановлена істина про стан реалізації. Його твердження при перенесенні
потребують перевірки так само, як твердження інших документів.

## 10. Що потрібно прийняти перед міграцією

- Чотири hex-позиції та першу цифру як номер поверху.
- Дефіс для імен; `_` лише як placeholder у тексті, поза реальними адресами.
- Попередню карту поверхів і резерв слотів `000`–`00F`.
- Стабільність адрес, один основний документ на адресу та збереження історії.

Ця чернетка пропонує ці рішення разом. Пілотні головні документи
`x0000`–`xF000` і адресний індекс створено як draft. Старі документи
не перенесено; код не перейменовано. Пілот не означає прийняття всіх контрактів.
